# 企业AI助手（Enterprise AI Assistant）

> 多 Agent 集群：一个统一问答入口，一个调度器，多个专业 Agent
> 用户只提问，不用关心"该找哪个助手"——由 AI 助手判断意图、分发给合适的 Agent，必要时组合多个 Agent 回答

## 统一调度设计

### 目标架构

```
前端（聊天端 frontend + 管理端 admin-frontend，均属于 ai-assistant 服务）
    ↓
ai-assistant（统一AI助手服务：调度器 + 统一问答接口）
    ├→ kb-agent             企业知识问答
    ├→ doc-review-agent     企业项目文档审查
    ├→ data-analysis-agent  企业数据分析
    └→ notice-agent         企业通知助手
```

- 用户只面对一个问答入口，由 AI 助手判断意图、分发、汇总
- 各 Agent 是独立服务，只通过统一协议与调度器通信

### 实施路径（2026-08-25 修订）

直接按最终形态建设：ai-assistant 从第一天就是独立调度服务，kb-agent 作为第一个被接入的 Agent，前端（Vite）属于 ai-assistant 服务。分步构建计划见 `ai-assistant/README.md`。

> 原方案（调度先内嵌 kb-agent，成熟后再拆出）已放弃——改为直接建独立服务，避免中途迁移。

### Agent 统一协议

每个 Agent 只暴露一个标准接口（内部随便实现）：

```
输入：{"question": "...", "context": {...}}
输出：{"answer": "...", "references": [...], "confidence": 0.9}
```

调度器只认这套协议，换 Agent、加 Agent 都不用改调度器。
内嵌阶段它是进程内函数调用的参数/返回值；拆分阶段它就是 HTTP 请求/响应体——形态不变。

### 调度器选 Agent

- LLM 意图识别输出 JSON（复用 classify_upload 模式）：`{"agent": "knowledge", "reason": "..."}`
- 识别失败/低置信 → 降级 knowledge
- 可扩展为 `{"agents": ["data", "knowledge"]}` 表示多 Agent 组合

### 多 Agent 组合

- 第一阶段：一个主 Agent + 可选辅助 Agent，并行调用，主 Agent 汇总
- 第二阶段（进阶）：串行依赖（A 的结果喂给 B）

### 第二个 Agent 选型

推荐先做 **doc-review-agent（文档审查）**：上传合同/方案/报告 → LLM 审查风险、给修改建议。复用现有文件解析能力，不依赖外部系统，能最快验证多 Agent 路由。（待确认）

## 知识库问答流程设计（kb-agent，2026-09-22 定稿）

> 语料现状（2026-09-22 记）：约 30 条知识 / 60+ 个向量块 / 正文合计约 1.5 万字，还在长（实时数字看管理端「数据」视角）。
> 语料还小，所以设计上先把「该看哪几篇」的主动权交给 AI + 人，而不是把检索算法做复杂。

```
用户提问
  │
聊天端 5173 ──→ 调度器 8001（意图识别=knowledge 且在线，否则兜底降级）──→ kb-agent 8003
  │
① 维度判断（LLM，失败降级 depth）
  │
  ├─ A｜深度 · 指定文档                                   【2026-09-22 已实现】
  │    聊天端左栏「指定文档」面板（默认收起 = 全库问答，勾选后随会话延续）
  │      → 面板打开 / 点「AI 预选」：目录（标题+分类+关键词）整体交 LLM 挑 ≤5 篇 → 默认勾选
  │        （目录超过 60 条时先向量粗排取 20 条候选，再交 LLM 挑）
  │      → 用户增删勾选（可零操作直接发）
  │      → 取数：勾选文档全文按标题组装 prompt（比分块检索完整）；
  │        正文总量超 12000 字 → 退回勾选范围内的向量检索
  │      → 回答；sources = 勾选文档，精确到篇、可溯源（气泡上标「按指定文档回答」）
  │
  ├─ B｜深度 · 自由问答（默认路）                                      【已有】
  │    问题向量化 → 全库块相似度 → 阈值 0.5 + 动态 k≤6 → 拼上下文
  │      → LLM 回答 → 零命中 或 含诚实短语 → 记入未命中
  │
  ├─ C｜广度 · 枚举                                                   【已有】
  │    查表按分类分组 → 列「标题【类型】(关键词)」清单 → LLM 组织成目录式回答
  │
  ├─ D｜广度 · 汇总 / 比较                                【2026-09-22 已实现】
  │    全部条目的「摘要」整体喂给模型做跨文档综合（不走向量检索——汇总要的是覆盖面，
  │    而相似度只会命中少数几条）
  │    （摘要 = 入库时生成/补录脚本补的 summary 字段，含关键数字；缺失则用正文首段兜底；
  │      摘要总量长大后约 >2 万字再按分类分批 map-reduce）
  │
  └─ E｜未知 · 未命中闭环                                   【2026-09-22 已实现】
       零命中 或 含诚实短语 → missed_questions（重复问累计次数）
         → 管理端「未命中问题」页点「补充」
         → AI 依问题起草骨架（只列要点、绝不编造具体规定，用【待补充】占位）
         → 人工填实 → 入库（自动向量化）→ 自动删除该条未命中 → 下次问到即命中
```

### 三条设计原则

1. **宽度问题不用向量检索**：向量相似度天然不擅长枚举与汇总（similarity ≠ coverage）——列举类走结构化查表（C），汇总比较类走摘要层整体喂（D）。
2. **勾选后直接全文喂**：语料小的时候，全文比分块检索更完整（不漏块、条款上下文完整），也不多花一次 embedding；勾选文档的正文总量超过 12000 字时自动退回“在勾选范围内检索”（`knowledge_vectors.source_id` 过滤，已实现）。
3. **AI 起草只搭骨架**：AI 不知道公司的真实规定，所以骨架里的数字/标准/流程一律用【待补充】占位，由人工填实——写错的资料会被当成正式制度回答给员工。

## 办公自动化（rpa-agent，2026-09-24 立项并落地骨架）

> 来源：公司业务的真实需求——OA 上的「加点流程」需要手工在金蝶网页版跨多个页面录入（供应商 → 手机号码 → 激活 → 分配车辆 → 收货地址 → 价格策略），一条流程含 1~n 条加点信息、每条十几项字段，全部做完才能回 OA 点批准。
> 定位：RPA 补的是"结构化输入 + 固定流程"的短板，LLM 补的是"理解与决策"——两边互补，是智能自动化的主流方向。

### 一条设计主线：LLM 管理解，脚本管执行，人管确认

```
LLM 负责"理解与映射"          →   RPA 负责"执行"              →   人负责"确认"
OA 里的非结构化内容 → 结构化字段    固定选择器脚本走各页面            提交前 / 批准前
字段对应目标系统的哪个输入项       每步留痕（状态/日志/截图）
```

- **执行动作不用模型临场决定**：填错一个供应商或价格策略，改起来比手工填还慢、还可能写脏生产数据。模型的价值在两头——前面把内容读懂、归一化、查缺，后面在元素定位失败时做视觉兜底（截图资料库就是素材）
- **形态是"有人值守的半自动"**：登录要过验证码，所以浏览器是 headful 的——人工登录一次、登录态落盘复用；执行过程人能看到、能随时接手

### 单元：把流程拆成可独立验证的最小块

**单元 = 一条业务数据 × 一个操作环节**。第一批业务单元（按依赖顺序叠加，前一个跑通再叠下一个）：

```
① 添加供应商 → ② 手机号码 → ③ 激活手机号码 → ④ 分配车辆 → ⑤ 收货地址 → ⑥ 价格策略分配
（之后再叠：⑦ 1~n 条加点信息循环 + 每步留痕  ⑧ 从 OA 取数（替换手工输入）  ⑨ 回 OA 点批准）
```

- 单元靠 `units/*.py` 里的 `UNIT` 声明 + `run(ctx)` 自动注册，加单元不改框架
- 运行时是**入队返回 run_id + 前端轮询**（就是本文档里写的"任务队列"形状），进度用「步骤列表 + 当前第几步」表达，不用会撒谎的百分比
- **双判定**才算跑通：系统断言（脚本没报错、页面回显对）+ 人工确认（打开目标系统核对过结果）

### 已知限制与待办

- 扫描件/大流程的耗时较长 → 与 kb-agent 一样，将来该上真正的任务队列（现在已是"入队 + 轮询"的形状，改造面很小）
- **写生产系统仍需 IT + 业务部门书面授权**：先在自己的系统上验证、再谈公司生产系统；正式跑之前用耗时对比数据去谈
- 真实单元的选择器等页面截图到位后逐个补（截图传「截图资料库」，AI 读图写选择器）

## RPA + Agent 更远的应用场景（2026-09-21 记的构想，仍待推进）

> 另一个来源：采购在 BIP 上的数据填报手工量大，填报前的 Excel / 表单数据也没有沉淀。
> 设想：用 RPA 替代重复录入，同时把数据采集下来，进入集群分类，成为企业可用、论文可用的数据资产。

### 两种结合形态

**采集侧（RPA → Agent）**

RPA 抓取页面 / Excel / 表单数据 → 集群内新增"数据处理 Agent"（分类、清洗、结构化）→ 进知识库或独立数据资产。
- 风险低、见效快；公司减负与论文数据两头都能兑现

**执行侧（Agent → RPA）**

用户自然语言指令 → 调度器识别意图 → RPA Agent 执行页面操作。
- 集群从"回答"到"做事"的演进；架构上只需新增一个服务（services.json + 调度器注册，manager 天然可守护）
- **必须有人工确认环节**：LLM 直接驱动页面向生产系统写入，幻觉一次就是错误操作；形态应为"Agent 生成操作预览 → 人确认 → RPA 执行"

### 前置条件与风险（均未解决）

1. 先查 BIP 是否自带 Excel 批量导入 / 开放接口——若有，直接用官方能力即可，不需要 RPA
2. RPA 写入生产 ERP 需 IT + 业务部门书面授权，并事先界定数据出错的责任
3. 微信沟通记录采集风险高（个人微信无官方接口、抓取违反腾讯协议且有封号风险；对话含商业与个人信息，涉及《个人信息保护法》）——合规路径是企业微信官方"会话内容存档"，个人微信建议放弃
4. 建议第一步走采集侧，先在自己的系统（如管理端）上验证，再谈公司生产系统

### 启动前要做的三件事

- [ ] 确认 BIP 官方导入 / 接口能力（可能一步到位，直接免掉 RPA）
- [ ] 选一种表单做最小验证：单次跑通，量准确率与耗时
- [ ] 用耗时对比数据去谈部门授权

## 统一服务管理（manager）设计

> 服务多了以后，每个服务占一个终端、状态靠肉眼盯不可持续——由 manager 守护服务统一管理各服务的启动、运行状态、自动重启、停止与日志

### 架构

```
你手动启动的（只有一个）
        │
┌─────────────────────────────────────────────┐
│  manager（守护服务，8002）                    │
│   起停控制 + 探活 + 自动重启 + 日志落文件      │
└──────┬──────────────┬───────────────┬───────┘
       │ 拉起/监控     │               │
┌──────▼──────┐  ┌────▼────────┐  ┌───▼─────────────┐
│ kb-agent    │  │ ai-assistant│  │ 前端（Vite dev）  │
│ 8000  RAG   │  │ 8001  调度器 │  │ 聊天 5173/管理 5174│
└─────────────┘  └─────────────┘  └─────────────────┘

管理端 5174（服务管理页）
     ├→ 8001 的 /api/v1/admin    ← 业务数据（统计、kb 管理，已有）
     └→ 8002 的 /api/v1/services ← 进程控制（新增，直连不代理——
                                    ai-assistant 挂了还得能重启它）
```

### 关键决策

- **manager 是根进程**：唯一手动启动的服务，不被任何被管服务托管；它自己的常驻守护后续交操作系统（Linux systemd / Windows 任务计划），现阶段挂了手动拉起
- **进程控制直连 8002**：不走 8001 代理（否则 ai-assistant 挂了无法重启它）
- **跨平台**：启动命令用 `{python}` / `{npm}` 占位符（manager 按系统解析为 `.venv\Scripts\python.exe`、`npm.cmd` 等真实路径），换操作系统 = 改配置不改代码；上 Linux 服务器后与 systemd 互补（systemd 管兜底，manager 管统一界面）
- **探活**：httpx 请求各服务的探活路径（配置项 `probe_path`——后端 FastAPI 用 `/docs` 零改动，Vite 前端用 `/`）
- **自动重启**：监控循环周期探活，进程死了自动拉起并计数；连续失败 5 次转 error 停止尝试（防端口冲突死循环）；手动 stop 的不自动拉起
- **服务清单即配置**（`manager/services.json`）：名称/端口/目录/命令/探活路径/是否随 manager 启动，另含管理页展示用的中文名（cn_name）与"进入"链接（enter_url），新 Agent 接入加一行即可

### 管理范围（2026-09-24 扩至八个进程）

kb-agent、ai-assistant、聊天端 5173、管理端 5174（Vite dev server 配 `probe_path: "/"`；`vite.config.js` 加 `strictPort: true`——端口被占直接报错，不自动换端口，否则 manager 按固定端口探活会"失联"；`host: '127.0.0.1'`——Vite 默认只绑 IPv6 的 localhost（[::1]），manager 探 IPv4 的 127.0.0.1 会连不上，实测踩坑后固定 IPv4 与后端一致）；2026-09-11 再把研读库前后端（study-agent 8003 / study-frontend 5175）纳入——共六个进程；2026-09-24 再把办公自动化前后端（rpa-agent 8004 / rpa-frontend 5176）纳入——共八个进程。services.json 每项另可配 `cn_name`（管理页中文名）与 `enter_url`（"进入"链接），管理端服务表格与架构图都从这里取数。生产环境前端（nginx）同为进程，照配置加一条即可。

## 待办与规划（2026-09-22 盘点）

### 1. 扫描件上传的任务队列【图文识别解析层 2026-09-24 已落地，队列待做】

- **已落地**：PDF 逐页判断有没有文字层——有 → pypdf 直接取字（免费、零转写误差）；没有（扫描件、图片页）→ PyMuPDF 渲染成图 → 大模型视觉转写；图片文件（png/jpg/jpeg/webp）本身就是"没有文字层的页"，直接走视觉
- **实测数据**：中文期刊 3 页扫描件，逐页与原文相似度 98.6%~99.3%；密排页原文 120 行全部命中、转写里没有一句原文没有的内容（无编造）；文本 PDF 仍走原路（0.3 秒，不产生视觉调用）
- **耗时现状**：A4 三页扫描件上传全链路 58 秒（视觉转写约 20 秒，其余是分类 + 向量化）；单张图片约 10 秒；密排长文档会到分钟级
- **待做**：上传改**任务队列**（入队返回 job id + 前端轮询），否则大扫描件会顶到前端 120 秒上传超时；顺带能解决"处理中"进度条只能做不确定动画的问题
- **调参记录**：视觉转写每批 4 页、输出上限 16000 token（实测密排 4 页需 4253 token，上限 8000 会截断，而截断一次要白等一分钟）；截断或整批请求失败时自动对半拆分重试
- **另记**：DeepSeek 只接受图片（webp/png/jpeg/gif）——PDF 直传、`file` 内容类型、`/files` 上传端点实测均被拒，所以"PDF 渲染成图"这步省不掉

#### 2026年09月24日【图文识别解析层落地 + 新增 rpa-agent（AI+RPA 办公自动化）与操作台】

**一、kb-agent 图文识别解析层（扫描件/图片能进库了）**

- **实现**：装 PyMuPDF → `file_parser.parse_pdf` 逐页判有没有文字层（该页字数 < 50 即判为扫描页）：有 → pypdf 直接取字（免费、零转写误差），没有 → PyMuPDF 渲染 150 DPI → 大模型视觉转写；图片文件（png/jpg/jpeg/webp）本身就是"没有文字层的页"，直接走视觉；`SUPPORTED_EXTENSIONS` 加图片、管理端上传框 accept 与 interfaces.js 同步。分类 / 摘要 / 向量化 / 问答链路**零改动**
- **`llm_service.transcribe_images`**：一次请求带多张图（每批 4 页），**输出上限 16000 token**——实测密排 4 页需 4253 token，上限 8000 会截断，而截断一次要白等一分钟（模型会一直生成到上限）；截断或整批请求失败时自动对半拆分重试；整篇转写失败抛错、不把占位提示当知识入库
- **实测**：中文期刊 3 页扫描件，逐页与原文相似度 98.6%~99.3%；密排页原文 120 行全部命中，转写里没有一句原文没有的内容（**无编造**——这条对知识库最重要）；文本 PDF 仍走原路（0.3 秒、不产生视觉调用）；A4 三页扫描件上传全链路 58 秒（视觉约 20 秒），单张图片约 10 秒。上传后提问能准确引用转写内容
- **验证性结论**：DeepSeek 只接受图片（webp/png/jpeg/gif）——PDF 直传、`file` 内容类型、`/files` 上传端点实测均被拒，所以"PDF 渲染成图"这步省不掉
- **踩坑记录**：自造测试扫描件时页面尺寸要写成点（A4 = 595×842），直接拿像素当点会让页宽变 17 英寸、渲染出 4 倍大的图导致模型转写跑飞
- 待办①相应改写为「扫描件上传的任务队列」（大扫描件分钟级会顶到前端 120 秒上传超时）

**二、新增 Agent：rpa-agent（办公自动化执行器）+ 操作台**

- **缘起**：公司真实流程——OA 上的「加点流程」要手工在金蝶网页版跨多个页面录入（供应商 → 手机号码 → 激活 → 分配车辆 → 收货地址 → 价格策略），一条流程含 1~n 条加点信息、每条十几项字段，全部做完才能回 OA 点批准。用户拍板做法：**先建服务 + 操作台，在操作台上一个模块一个模块地验证叠加**（操作台同时当"截图资料库"用，供 AI 识别页面结构写选择器）
- **服务**：`rpa-agent/`（8004，FastAPI + SQLite + Playwright）、`rpa-agent/frontend/`（5176 操作台，技术栈照管理端）→ **manager 守护八进程**
- **核心结构**：`core/browser.py` 的 `BrowserWorker` 把 **Playwright 同步 API 锁在一条专用工作线程**，所有任务走同一条队列串行执行——从结构上杜绝"同步调用冻住事件循环 → 探活超时 → 被 manager 反复重启"那个老坑（kb-agent 踩过），同时把"浏览器同一时刻只能被一个操作驱动"的互斥变成队列白送；浏览器**懒加载**（避开 30 秒启动窗口）、headful + 系统 Edge（`channel="msedge"`，免下载 chromium）、`data/browser_profile` 持久化登录态（验证码人工过）
- **单元模型**：单元 = 一条业务数据 × 一个操作环节；`units/*.py` 里声明 `UNIT`（key/中文名/次序/环境/输入字段/步骤）+ `run(ctx)`，靠 `core/registry.py` 自动注册——**加单元不改框架**。`ctx.step(key)` 用 with 语法：进来自动标"进行中"，出来自动标"成功"，出异常自动标"失败"并截图 + dump HTML 留现场；选择器集中在文件顶部 `SEL` 字典
- **运行模型**：`POST /api/v1/units/{key}/run` 建记录 + 投队列 + 立刻返回 `run_id`，前端轮询 `GET /api/v1/runs/{id}`——正是本文档里写的"任务队列"形状（入队返回 id + 轮询），进度用「步骤列表 + 当前第几步」表达，不用会撒谎的百分比；SQLite 三表（runs / run_steps / unit_meta）、每步截图与 `logs/run_{id}.log`、服务启动时把遗留的"执行中"标成 `interrupted`、取消是协作式（步与步之间检查开关，不硬杀）
- **双判定才算跑通**：系统断言（脚本没报错、回显对）+ 人工确认（打开目标系统核对过结果，操作台上点「标记为已跑通」写 unit_meta）——真实单元光看"页面提示保存成功"不算数
- **操作台两页**：执行台（浏览器状态与人工登录 / 单元清单 / JSON 输入 + 运行 + 实时步骤与日志与截图 / 标记已验证）、截图资料库（上传页面截图存 `data/shots/`，供 AI 读图写选择器）
